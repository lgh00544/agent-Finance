# 业务名 ↔ 物理表名映射（命名澄清）

> **用途**：仓库的文档 / 提示词 / 前端里出现的「业务叫法」与 SQLAlchemy 模型的**物理表名**并不总是一一对应；
> 本表把已核实的历史误称与常见易混名一次写清，供写 SQL、写报告、写新文档时对照。
> **证据基线**：`backend/app/db/models.py`（2026-10-06 工作树行号，逐类核对 `__tablename__` 与类 docstring）。
> **纪律**：本文只做命名澄清，**不改任何表结构 / 字段名 / 业务行为**；新代码与新文档一律以物理表名为准。

## 一、三组历史误称（必须改正）

| 误称（文档 / 口头） | 实际物理对象 | 证据 | 说明 |
|---|---|---|---|
| `candidate_snapshot`（当成一张独立表） | `stock_candidate` 表的 **`snapshot` 列**（SafeJSON） | `models.py:76-78` 类 `StockCandidate`、`models.py:91` | 候选池没有快照表：当日原始行情快照存 `stock_candidate.snapshot`，v2.0 输出详情存 `detail`（`:92`）。查「某日候选快照」= `select * from stock_candidate where trade_date = ?`。 |
| `stock_plan` | **`position_plan`** | `models.py:218-220` 类 `PositionPlan` | 建仓方案的物理表名是 `position_plan`，`stock_plan` 在库里不存在。状态 `status` ∈ proposed / accepted / expired / superseded（`:226`）；量化明细在 `detail.quant`（`:232`）。 |
| `position_monitor`（当成一张独立表） | `ai_reasoning_trace` 里 **`source_module = 'monitor'`** 的行 | `models.py:333-341` 类 `AiReasoningTrace`、`models.py:352`、唯一键 `:343` | 持仓监控没有独立留痕表：全模块共用 `ai_reasoning_trace`，用 `source_module` 区分 `discover / score / position / monitor / alert / review / sell`；唯一键 `(user_id, stock_code, generate_date, source_module)`；追加历史在 `ai_reasoning_trace_history`（`:367-373`）。 |

## 三、使用约定

1. 写 SQL、写报告、写新文档一律用**物理表名**；UI / 口头业务叫法可在本文登记后继续使用。
2. `candidate_snapshot` / `stock_plan` / `position_monitor` 三个叫法**作废**：检索历史文档时按 §一 映射理解，新文档不得再使用。
3. 发现新的误称 → 追加到 §二（附物理表名 + `models.py` 行号证据），不要另开命名体系。
4. 本文不授权任何 DDL / 迁移变更；表结构以 `models.py` 与迁移脚本为准。
