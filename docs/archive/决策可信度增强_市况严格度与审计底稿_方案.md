---

## 背景：claw 协同方式带来的启示

sir 提供了一段此前 claw（另一个智能体）的协同汇报样例，核心价值不在格式花哨，而在**四层决策纪律**：

| claw 维度 | claw 做法 | 我们系统现状 | 采纳与否 |
|---|---|---|---|
| 差异一 · 市况先判 | 先判大盘档位（好/中/坏/极差）→ 决定选股激进/保守 + 严格度 | 已有 4 档 market_cap_bands，但只映射「候选池上限」，未映射「严格度」，档位名不直观 | ✅ 采纳，升级现有骨架 |
| 差异二 · 审计底稿 | 逐条通过/拒绝 checklist 留痕，谁没过/为什么/降到哪档 | 只有 judge_tradeable 的 block_reason 一句话 | ✅ 采纳（本次重头） |
| 差异三 · 认错-复犯闭环 | K184 v+1，错误类型累计，回写规则 | 无 | ⏸ 后续优化（初步阶段人工可控，不自动化） |
| 差异四 · 证据引用 | 判断绑定具体数字（"沪电 +6% 量能 2.6%"） | dimensions 有分数无依据数字 | ✅ 采纳 |

---

## 目标（本次落地）

1. **宏观市况分档直观化 + 严格度档位**：把现有 4 档 market_cap_bands 从「只控候选池上限」升级为「候选池上限 + 选股严格度」，档位名改直观（防御/过渡/温和/强势 → 极差/坏/中/好），并把「严格度」作为决策刻度注入 Discover LLM prompt 与 judge_tradeable。
2. **审计底稿双层落库**：
   - **A 层（候选生成层）**：每只候选 detail 增加 `audit` 结构化字段，含关键判定链（市况是否允许 / tier / 止损 / 盈亏比 / 风险 / 通过与否）。
   - **B 层（可建仓判定层）**：`block_reason` 从一句话升级为结构化「拒绝明细数组」，每项含 {条件, 是否通过, 依据/数值}。
3. **前端可展开审计卡片**：候选池每行可点击展开，内见「市况档位徽章 + 各维度依据 + 判定勾选明细」。
4. **合规底线**：只加字段展示与刻度映射，**不改变五维评分的维度定义、不改变候选池真实排序结果、不改变交易规则/研判标准表**，所有改动可经 review_log 回滚。

## 一、市况严格度档位（差异一落地）

### 1.1 现状（既有，不推翻）
`backend/app/core/config.py:90` `market_cap_bands` 现有 4 档：

| 分数区间 | 候选池上限 | 当前档位名 |
|---|---|---|
| 0-20 | 5 | 防御期 |
| 21-35 | 10 | 过渡期 |
| 36-45 | 15 | 温和期 |
| 46-50 | 20 | 强势期 |

现有 `market_band_info(score)` 返回 `(cap, name)`，仅消费于 `discover.py` 的候选池上限截断。

### 1.2 升级方案（加一维 strictness，不改得分算法）

> **sir 已拍板（15:28）：严格度基准 = 五维评分分档为主 + MarketIntel 修正。**
> 即：先由 `market_cap_bands` 分数区间得出基底严格度；再读取当日 `market_intel.risk_appetite`（进取/中性/避险）与 `phase`，按修正规则上调/不变。MarketIntel 缺失时不修正、退化为基底严格度（保证单数据源失败不瘫痪）。

**档位结构扩展为 5 要素**：`[低分, 高分, 候选池上限, 档位名, 宏观定级, 严格度]`

| 分数区间 | 上限 | 档位名 | 宏观定级 | 严格度 strictness |
|---|---|---|---|---|
| 0-20 | 5 | 防御期 | 极差 | 极严（limit_candidates）|
| 21-35 | 10 | 过渡期 | 坏 | 严格（strict）|
| 36-45 | 15 | 温和期 | 中 | 标准（normal）|
| 46-50 | 20 | 强势期 | 好 | 宽松（aggressive）|

- `strictness` 枚举：`极严/严格/标准/宽松`（映射到英文 tag：`extreme/strict/normal/aggressive`，前端徽章用）。
- `market_band_info` 返回值扩展为 `(cap, band, grade, strictness)`。
- **⚠️ 兼容性铁律（P0）**：Python 双变量解构 `cap, band = market_band_info(x)` 遇 4 元组返回会抛 `ValueError: too many values to unpack`，**不会自动忽略多出的元素**。因此改返回签名必须**同步**改所有调用方为 `cap, band, *_ = market_band_info(x)`：
  - `backend/app/agents/discover.py:174` 和 `:187`（现 `cap, band = ...`）
  - `backend/app/db/repo.py:193` 和 `:211`（现 `cap, band = ...`）
  - `tests/test_discover_v2.py:24-32`（现断言 `== (5, "防御期")` 2 元组，改 4 元组 `(5, "防御期", "极差", "极严")` 并存档 boundary 测试）
  - 另**全仓 grep** `market_band_info(` 确认无遗漏调用方（含 `.env` JSON 覆盖 `MARKET_CAP_BANDS` 时列结构需同步加 2 列）。

### 1.3 严格度注入点（两处）

**注入点 1 — Discover LLM prompt**（`discover.py` 的 `_market_note` 或市况注入段）：
- 现状：`今日市况评分 X 分（档位），候选池上限 N 只`
- 升级为：`今日市况评分 X 分（档位名，宏观定级），候选池上限 N 只。市况定级【好/中/坏/极差】→ 选股策略应【宽松选股·宽松门槛 / 标准选股·常规门槛 / 严格选股·从严门槛 / 只保留最强信号·极严门槛】`
- 措辞模板放 config 或 prompt 常量，按 strictness 选择。

**注入点 2 — judge_tradeable**（`backend/app/services/candidate_tradeable.py`）：
- 现状：`cond_grade = 1 if tier_effective in ("A","B")` 只看 A/B 档。
- 升级：把当日 strictness 传入，作为「门槛刻度」。例如：
  - 宽松：tier ∈ A/B/C 均可建仓候选（C 仅观察不建仓——保持现状）。
  - 标准：维持现状（A/B 建仓）。
  - 严格：仅 A 建仓，B 降为观察；且多一条「历史 T+5 胜率 ≥ 40%」硬校验（超过关卡）。
  - 极严：仅 A 且「历史 T+5 胜率 ≥ 50% + 主力净流入 ≥ 1 亿」双重关卡，从严校验。
- **要点**：严格度只影响「可建仓门槛」，不改变候选生成与排序本身。冻结规则写 review_log。
- **边界铁律（P0，与"不改排序"红线分离）**：严格度**只改 `judge_tradeable` 的 `is_tradeable` 判定结果**（可建仓/不可建仓），**绝不改候选 `rank` 排序分数**（universe 排序、候选生成顺序都不动）。"不改排序"= 不改 rank 分数；"可建仓判定集合"变化 ≠ 排序变化，执行端不得因加了严格度门槛而顺手动排序逻辑。若某票因严格度从"可建仓"变"不可建仓"，只是 `is_tradeable=0` + 对应 block_details 的"严格度门槛"一项 passed=false，`rank` 与其他候选的相对位置不变。

### 1.4 MarketIntel 修正规则（五维基底 + 宏观修正）

**新增 `apply_market_intel_correction(base_strictness, market_intel) -> final_strictness` 纯函数**，规则如下（冻结写 review_log）：

| 基底严格度 | risk_appetite=避险 | risk_appetite=中性 | risk_appetite=进取 |
|---|---|---|---|
| 宽松(好) | 上调→标准 | 不变→宽松 | 不变→宽松 |
| 标准(中) | 上调→严格 | 不变→标准 | 不变→标准 |
| 严格(坏) | 不变→严格 | 不变→严格 | 不降（保持严格）|
| 极严(极差) | 不变→极严 | 不变→极严 | 不降（保持极严）|

**修正规则要点**：
- **只允许"上调"或"保持"，禁止"因进取而放宽市况"**：
  - 严格/极严基底的进取不得降档（claw 的"防御期不因乐观而降级"理念）；
  - **标准基底也不允许进取下调到宽松**（P1 收紧：30+ 分的"中市况"不应被当成宽松门槛，与"好市况才宽松"直觉一致）——进取最多保持标准。
- 宽松基底可因避险上调（反映宏观情绪转防守）；标准基底可因避险上调、可保持（进取不再下调）。
- 读取：`repo.get_market_intel(trade_date)`，若返回 None 或 risk_appetite 不在三态 → 不修正，返回 base。
- `phase` 作为次要信号：若 phase 含「退潮/出货/弱势/存量博弈」关键词（黑名单），即使 risk_appetite=进取也不下调，保持基底严格度。

**函数放置**：`backend/app/core/config.py`（与 market_band_info 相邻）或 `backend/app/services/market_intel_correction.py`（新增，解耦）。

### 1.5 配置项
- 在 `config.py` 的 `market_cap_bands` 加一列 strictness（`.env` 用 `MARKET_CAP_BANDS` JSON 覆盖时需同步列结构）。
- 新增 `strictness_policy` 常量表：`{strictness: {tier_allowed:[...], extra_checks:[...], prompt_phrase: "..."}}`。
- 新增 `market_intel_correction_map`：上表映射常量 + `phase_blacklist`（退潮/出货/弱势/存量博弈）。

## 二、审计底稿双层（差异二落地，重头戏）

### 2.1 A 层：候选生成层 audit 字段

**位置**：`backend/app/agents/discover.py`（候选 detail 构造块，约 L634）+ 可选 Score。

**新增 `audit` 结构化字段**（写入每只候选的 detail，JSON）：

```json
{
  "audit": {
    "trade_date": "2026-08-21",
    "market": {"score": 30, "band": "过渡期", "grade": "坏", "strictness": "严格", "cap": 10},
    "decisions": [
      {"key": "market_gate",      "label": "市况门槛",         "passed": true,  "evidence": "市况30分/坏/候选上限10"},
      {"key": "tier_gate",        "label": "评级档位",         "passed": true,  "evidence": "confidence_tier=建议关注"},
      {"key": "stop_loss",        "label": "止损约束",         "passed": true,  "evidence": "止损-8% 在约束内"},
      {"key": "profit_risk_ratio","label": "盈亏比≥2:1",      "passed": false, "evidence": "目标33/止损32.5 → 盈亏比1.5"},
      {"key": "major_negative",   "label": "重大利空排查",     "passed": true,  "evidence": "无公告负面"},
      {"key": "pool_position",    "label": "位置(距52高)",     "passed": true,  "evidence": "距52高 -5.2% 吸筹区"}
    ],
    "verdict": "建议关注",           // 最终定性
    "passed_ratio": "5/6",            // 通过项计数
    "note": "综合4/5维支持，可低吸；盈亏比不足需回调至更优价位"
  }
}
```

- **decisions 项可配置**：核心 6 项 = 市况门槛 / 评级档位 / 止损约束 / 盈亏比 / 重大利空 / 位置。每项 `passed + evidence`。
- **verdict 与现有 confidence_tier 联动**：verdict 默认等于 confidence_tier。
- **严格度影响 verdict**：若 strictness=极严 且 passed_ratio < 5/6 → verdict 降一档（建议关注→观察），并写 note 说明「降档原因：严市况下未全项通过」。

### 2.2 B 层：可建仓判定层拒绝明细

**位置**：`backend/app/services/candidate_tradeable.py` 的 `judge_tradeable`。

**当前**：返回 `{is_tradeable, label, block_reason(字符串), cond_*}`。

**升级**：`block_reason` 保留（前端兼容），**新增 `block_details` 结构化数组**：

```json
"block_details": [
  {"rule": "市值/流动性", "passed": true,  "evidence": "成交额 3.2亿 ≥ 1亿"},
  {"rule": "止损条件单",   "passed": true,  "evidence": "cond_price 32.5 已设"},
  {"rule": "风险红线",     "passed": false, "evidence": "detail.risks 含追高回撤"},
  {"rule": "严格度门槛",   "passed": false, "evidence": "strictness=严格, 仅A可建仓, 该票为B"}
]
```

- `is_tradeable` 最终 = 各 passed AND；任一 false 则不可建仓，`block_reason` = 拼接失败的 rule + evidence。
- **落库路径（P0 明确）**：`block_details` 放 `detail["block_details"]` JSON 内承载（`candidate_tradeable` 表的 `detail` 列是 JSON，repo.py:427 已读 `r.detail`）。**不改 `upsert_candidate_tradeable` 签名、不新增平铺列**。前端从 `r.detail.block_details` 读，`block_reason` 平铺列保留给旧读取方（CandidatesPage.tsx:642 / batch_chat / 测试）。

### 2.3 兼容性铁律
- **detail 写入路径（P1 修正，非整覆盖）**：`discover.py:673` 已是 `detail = {**existing, **new_detail}` 防御式 merge（V3.0 已在此层修过 P0-4 丢键坑），`existing` 来自 `repo.get_candidate_detail`。真正的整覆盖在 `repo.upsert_candidate` 内部（repo.py:81 `row.detail = detail`）。因此：
  - audit 作为 `new_detail` 里的一个**完整子 dict** 一次写入即可自动 merge，无需"一次性构造全部字段那么紧张"；
  - 但 **audit 子 dict 内部仍需完整**（6 项 decisions 齐全，缺项=audit 内丢键）；
  - **禁止动 `repo.upsert_candidate` 内部**（被 Score/Monitor/ExperienceWorker 共用）——这是硬红线。
- block_details 放 **detail 内字段** `detail["block_details"]`（`CandidateTradeable.detail` 是 JSON 列，repo.py:427 可读），**不新增平铺列、不改 `upsert_candidate_tradeable` 签名、不破坏 `block_reason` 既有读取方**（CandidatesPage.tsx:642 / batch_chat / 测试均只读平铺 block_reason）。
