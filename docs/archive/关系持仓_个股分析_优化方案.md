## 0. 现状摸底（结论先行）

读了一遍 `agent_prompts/` + `streamlit/pages/` + `base_file/` 知识库，得出三个关键事实：

### 0.1 "关系持仓"和"个股分析"已经在 Agent 层有，但各自单点，未形成闭环

| 维度 | 现有实现 | 已落地 | 待优化 |
|---|---|---|---|
| 关系持仓·板块退潮 | `portfolio_sentinel.py` + `portfolio_sentinel_prompt.py`（批次 1） | ✅ | 板块数据缺失兜底 + 拉宽到跨板块联动 |
| 关系持仓·组合回撤联动 | SellAgent `portfolio_risk_context` 注入（批次 2） | ✅ | 维度归因未把组合级展开 |
| 关系持仓·时间止损 | PortfolioSentinel 时间止损评估 | ⚠️ 已有 | 横盘 ±2% 阈值硬编码，未与"超买/超卖"联动 |
| 关系持仓·集中度 | PortfolioSentinel 集中度预警 | ✅ | 阈值 40% 单一行业，未做子行业/题材维度 |

| 个股分析·复盘 | ReviewAgent + track_verify | ✅ | 跨期回看未做"组合级 vs 个股级"对比 |

### 0.2 知识库侧已经把判断逻辑写得很细，但未落到 Agent Prompt 里

- **K 红线 K1-K227**：223 条永久红线，其中 **C1/C2/C3/C4 + K47/K138/K139/K168/K175/K185/K189/K192/K196/K226/K227** 直接关联持仓/个股判断。
- **持仓知识库 v1.0**：C3 止损 = 成本 × 0.92，K139 SOP 持盈不持亏，K189 主力 7+2 骗局识别，K226 9 大主体判定，K168 三维分析，K138 5 维超买/4 维超卖。
- **游资大佬追踪体系**：K226 第 ② 主体，对倒识别 4 信号，胜率统计，**但当前 Agent 仅在 prompt 框架里给了 K226 第 ② 主体的概念，无真实数据接入**。

### 0.3 关键缺口（本次优化要补的）

1. **判断标准散落**：C3、K139、K47、K189、K226 等红线在 Agent prompt 里只是原则性引用，缺少"可执行的判定阈值 + 数据校验口径"。
2. **个股 ↔ 组合 联动单向**：SellAgent 已读 PortfolioSentinel 快照，但 **MonitorAgent/ReviewAgent 还没读到**；组合级结论没回流到 Monitor 的"个股状态标签"。
3. **游资数据源未接入**：5_游资追踪.py 已有占位但 `dragon_tiger_source` / `capital_flow` 表是否真正跑通需复核；个股判断时无"游资净买/对倒/撤离"的实时事实。
4. **复盘未做"组合 vs 个股"对比**：track_verify 只做了胜率统计，没有"组合回撤分解 = 各持仓贡献度"——sir 关心的"哪只票拖累组合"看不出来。
5. **派发期判定未自动化**：K47 派发期 5 阶段、K175 派发期 6 维、K185 Spring 反弹——全是 prompt 文字，没有代码层"派发期判定结果"字段可注入。

## 一、优化目标（5 大目标，对应 sir 拍板的判定哲学）

1. **判断可执行**：所有红线（K47/K138/K139/K168/K175/K189/K226/K227/C1-C4）从"prompt 原则"升级为"代码可注入的事实字段 + LLM 解读"双层结构。
2. **关系持仓真联动**：PortfolioSentinel → MonitorAgent → SellAgent → ReviewAgent，**单向只读链路打通**，每段判断都引用上一段产出。
3. **个股分析有事实**：游资维度从 prompt 概念升级为有数据源、有落库、有注入；基本面/技术/资金/舆情/行业五维全部"代码计算 + LLM 解读"分层。
4. **派发期自动判**：派发期 5 阶段从"人肉看 K 线"升级为代码层判定的 `distribution_phase: 0-5` 字段，注入所有 Agent。
5. **复盘反哺选股**：组合回撤分解到各持仓贡献度 + 同标的多次操作的"周期复利"分析，回流到 ScoreAgent 的"历史胜率"维度。

## 三、5 大优化模块（按优先级排序）

### 模块 1：派发期自动判定（最优先·代码层新建设）

**问题**：K47/K175/K185 派发期判定现在全靠人肉看 K 线，prompt 里只有原则，没有"派发期 = X"的注入字段。

**目标**：代码层算出 `distribution_phase: 0|1|2|3|4|5`（对应拉升期 0 + 派发期 1-5 触底期），注入所有 Agent。

**要做的事**：

1. **新增 `backend/app/services/distribution_phase.py`**（参照 `holding_view.py` 的纯计算风格）
   - 输入：标的过去 60 日 K 线 + 板块行情 + 主力资金净额
   - 计算口径（参考 K175 派发期 6 维）：
     - 时间维度：5 日累计涨跌幅 / 20 日累计涨跌幅
     - 空间维度：距 52 周高 / 距 52 周低
     - 量价维度：量价背离 / 量价配合
     - 主力维度：5 日主力净流入趋势
     - 形态维度：近 10 日 K 线反转形态计数
     - 政策维度：近 30 日政策事件数（占位，无数据标 None）
   - 输出：`{"phase": 0-5, "phase_label": "拉升期/初期/砸盘期/反弹期/末跌期/触底期", "confidence": "高/中/低", "six_dim": {...}, "missing_data": [...]}`
   - **纪律**：数据缺失字段必须在 `missing_data` 中明列，`confidence` 自动降级，**绝不编造数值**。

2. **代码层新增 `repo.py` 函数**：`get_latest_distribution_phase(stock_code)` 读最近一次判定结果（缓存到 `cache`，TTL 24h）。

3. **注入点**（3 处）：
   - `MonitorAgent.collect_quote`：在 `quote_data` 段追加 `【派发期判定】{phase_label} (置信度 {confidence}) + 6 维原始数据`
   - `SellAgent.collect_sell_input`：在 `portfolio_risk_context` 后追加 `distribution_phase_context` 段
   - `ScoreAgent.collect_score_input`：5 维评分时把"派发期判定"作为"风险维度"参考（不单独占一维，避免归因重复）

4. **定时任务**（`jobs.py`）：
   - 每日 15:30（收盘后）跑一遍所有"今日候选 + 当前持仓"的派发期判定，结果落 `distribution_phase_log` 表
   - 触发：持仓或候选 + 距上次判定 ≥ 1 日 + 行情已更新

5. **Schema/接口**：
   - `schemas.py` 追加 `DistributionPhaseOutput`
   - `routes.py` 追加 `GET /api/distribution_phase/{stock_code}` 单独查询接口（手动触发重算）

**红线**：
- 不改现有 Agent 结构（仅 collect 段追加一行）
- 数据缺失必标 `missing_data`，不编造
- 不影响 K22（动态参考线非死条件）
- 派发期判定置信度低时，`phase_label` 加 `?` 后缀（如"拉升期? "），前端徽章变灰

**验收**：
- 任一标的跑 `GET /api/distribution_phase/{code}` 返回完整 6 维原始值 + phase + confidence
- 持仓表注入派发期徽章，红/黄/绿/灰四态
- MonitorAgent prompt 实际包含 `【派发期判定】` 段（grep 验证）

### 模块 2：游资数据真接入（个股分析·资金维度事实化）

**问题**：游资维度在 prompt 框架里给了 K226 第 ② 主体的概念，但 `dragon_tiger_source` / `capital_actor` / `capital_flow` 三张表是否真正跑通需复核；SellAgent 的"游资撤离"判断现在没有事实依据。

**目标**：游资维度 = 有数据源 + 有落库 + 有注入 + 有徽章。

**要做的事**：

1. **复核** `backend/app/datasource/` 是否有 `dragon_tiger_source.py`，`backend/app/db/models.py` 是否有 `capital_actor` / `dragon_tiger` / `capital_flow` / `capital_stats` 四张表（按 `base_file/游资维度嵌入需求规格_2026-08-09.md` §1）。
   - 若未实现 → 落本次补
   - 若部分实现 → 补全缺口（数据源 / 聚合 / 统计）

2. **新增 `backend/app/services/capital_view.py`**（参照 `holding_view.py` 风格）
   - 输入：股票代码 + 时间范围
   - 输出：`{"recent_actors": [{name, tier, net_buy, days_active}], "coordination": "多游资同买 / 单家动作 / 无显著动作", "stats_30d": {胜率, 盈亏比, 平均持仓天数}, "theme_resonance": True/False, "missing_data": [...]}`
   - **纪律**：30 日内无数据 → `recent_actors: []`，`coordination: "数据不足"`；**绝不把"无数据"写成"无动作"**。

3. **K189 对倒识别代码化**（K189 ⑥）
   - 同一标的近 5 个交易日：若同一营业部出现在买入 + 卖出两侧 → 标 `suspect_wash_trade: True`
   - 阈值：单次金额 ≥ 1000 万
   - 这是**纯代码判定**，不交给 LLM；LLM 只负责"对倒对操作的影响"解读

4. **注入点**（4 处 Agent）：
   - `DiscoverAgent`：候选池评分时 `capital_flow` 段（题材共振加分）
   - `ScoreAgent`：5 维评分中"资金/游资"维度追加 `capital_view` 摘要
   - `MonitorAgent`：持仓标的被游资关注/撤离时输出对应信号
   - `SellAgent`：游资大幅净卖 + K189 出货验证 → 减仓信号（已有原则，补事实）

5. **5_游资追踪.py 前端增强**
   - 增加"标的-游资-战绩"三维表
   - 持仓标的被游资关注 → 持仓监控页挂黄色徽章
   - 持仓标的被游资撤离 + 触发对倒 → 红色徽章

**红线**：
- 不硬绑席位映射（未知营业部 → LLM 研判占位）
- 单源数据 → 标注 `source: "sse_only"` 等，触发 K227 多源验证缺失警示
- 游资跟买 ≠ 必胜（K225 诚实），prompt 不变，事实层更厚

**验收**：
- `curl GET /api/capital_view/{code}` 返回完整数据，缺数据字段全列
- 任一持仓标的 ScoreAgent 实际包含 `【游资本周动向】` 段（grep 验证）
- 5_游资追踪.py 能展示"该游资历史胜率 + 最近动作标的"
- 评分页"资金/游资"维度分数能反映游资事实（之前维度挂 0 现在能挂分）

### 模块 3：组合级 ↔ 个股级 联动链路打通

**问题**：SellAgent 已读 PortfolioSentinel 快照（批次 2 完成），但 MonitorAgent / ReviewAgent 还没读；组合结论没回流到 Monitor 的"个股状态标签"。

**目标**：组合级产出（板块退潮 / 集中度 / 回撤）穿透到 MonitorAgent 的告警标签 + ReviewAgent 的复盘归因。

**要做的事**：

1. **PortfolioSentinel 输出结构升级**（仅追加字段，不动判断逻辑）
   - 在 `portfolio_sentinel.py` 节点末尾追加：
     ```python
     cache.set("portfolio_sentinel:last_full", result, 1800)  # 含 4 维全部输出
     cache.set("portfolio_sentinel:last_sector_alerts", result.get("sector_alerts", []), 1800)
     cache.set("portfolio_sentinel:last_concentration_alert", result.get("portfolio_risk", {}).get("concentration_alert"), 1800)
     ```
   - **不改 PortfolioSentinel 判断逻辑、不改 schema、不改 prompt**

2. **MonitorAgent 接入组合上下文**（collect 段追加 1 段）
   - `monitor.py` `collect_quote` 末尾追加读取 `portfolio_sentinel:last_sector_alerts`
   - 若当前持仓股出现在 `sector_alerts` 中 → 在 `quote_data` 段追加：
     ```
     【组合级预警】该股所属板块 {sector} 触发板块退潮（量比 {volume_ratio}，alert_level {level}）
     ```
   - 若 `concentration_alert=True` 且同板块持仓 ≥ 2 只 → 追加：
     ```
     【组合级预警】同板块持仓集中度超 40%，建议减仓优先考虑同板块标的
     ```

3. **ReviewAgent 接入组合级上下文**（collect 段追加 1 段）
   - `review.py` `collect_review_input` 末尾追加读取 `portfolio_sentinel:last_risk`
   - 复盘归因维度新增"组合级贡献"：每只持仓对当日组合盈亏的贡献度（= 单票盈亏 / 组合总盈亏 × 100%）
   - 顶部展示条："今日组合 {total_pnl_pct}%，最大贡献者 {top_contributor} ({pct}%)"

4. **缓存键规范**（统一管理避免脏读）
   - 在 `backend/app/cache.py` 加注释列出所有 `portfolio_sentinel:*` 键、TTL、写入方、读取方
   - SellAgent / MonitorAgent / ReviewAgent 读这些键时做 `try/except`，缺失时降级为"组合数据不可用"不影响个股判断

**红线**：
- 单向只读：MonitorAgent/ReviewAgent 读 PortfolioSentinel 缓存，不反向调用其图/节点/router
- PortfolioSentinel 节点逻辑零改动（仅追加 `cache.set`）
- SellAgent 读 PortfolioSentinel 是批次 2 已完成，本次**不动**

**验收**：
- `grep "组合级预警" backend/app/agents/monitor.py` 命中
- `grep "组合级贡献" backend/app/agents/review.py` 命中
- PortfolioSentinel 节点末尾 `cache.set` 调用 ≥ 3 个键
- 缓存键注释文档化

### 模块 4：K 红线代码化（持仓知识库 v1.0 落地）

**问题**：C1/C2/C3/C4 + K139 SOP + K47 派发期 + K189 主力骗局 + K226 9 大主体判定——这些都在 prompt 里以原则形式存在，但**没代码层字段可注入**。结果 LLM 经常"凭印象"判断而不是基于事实。

**目标**：高频红线升级为"代码可注入的事实字段"，LLM 只负责"基于事实的解读"。

**要做的事**：

1. **新增 `backend/app/services/red_line_check.py`**（纯计算）
   - 输入：持仓 + 当前价 + 组合行情
   - 输出字段（每个持仓一行）：
     ```python
     {
       "stock_code": "601138",
       "c1_cap_pct": 17.6,            # 当前占总资产比例
       "c1_alert": False,             # ≤ 60% 触发
       "c2_alert": False,             # ≤ 30% 触发
       "c3_stop_loss": 59.00,         # 成本 × 0.92
       "c3_alert": False,             # 当前价 ≤ C3 触发
       "c4_high_break": True,         # 是否突破持仓期最高价（用于 +5%/+10% 触发判定）
       "pnl_pct": 1.86,               # 当前浮盈亏
       "k139_sop": {                  # K139 SOP 持盈不持亏
         "trailing_stop": 65.17,      # 成本 + (现价 - 成本) × 0.5
         "stage": "持有观察",         # 试探仓 / 持有观察 / +5% 减仓 / +10% 减仓 / 跌破 C3
         "next_action": "持有观察",   # 当前价位应执行的动作
       },
       "k226_subject_count": 0,       # 9 大主体中减仓数
       "k226_alert_level": "无",      # 无 / 中等派发 / 强派发
       "k189_wash_suspect": False,    # 对倒嫌疑（需游资数据，见模块 2）
     }
     ```
   - **纪律**：所有数值字段 null 显式标 null，前端显示"—"，不伪造 0
