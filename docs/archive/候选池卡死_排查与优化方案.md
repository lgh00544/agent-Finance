## 一、问题现象（父亲反馈）

1. **每日候选池页面停在 2026-08-10**，8/11、8/12 没更新。
2. 今早 11:17 在界面手动点了一次「每日挖掘」，**到现在（13:20）2 小时没跑完**，候选池仍停在 8/10。
3. 8/10 晚那条候选池是 23:14 **手动**生成的（created_at=2026-08-10 23:14:46），不是 16:10 定时任务产的。

## 二、排查结论（已排除的 + 已定位的根因）

### 已排除（证据充分，不是这些原因）
- ❌ **不是没挂梯子连不上库**：直连云端 TiDB（gateway01...tidbcloud.com:4000）成功，`news_article` 有 8/12 10:05 的最新数据。连库不需要代理。
- ❌ **不是数据库不更新/读库缓存**：`fetch_latest_announcement("601138")` 实测返回 13 条，含 8/12 当天 3 条；`repo.get_recent_news` 也正常。读库链路完全 OK。

### ✅ 已定位的根因（证据链完整）
**根因：8/12 11:17 手动触发的 discover 任务卡死了（status=running，2 小时未完成），它占着 `daily_pipeline` 的任务锁，导致后续所有 discover 请求全部 409 拒绝，候选池无法更新。**

证据：
- `GET /api/tasks/recent` → 显示 `id=c9f487ff47b2, kind=daily_pipeline, status=running, submitted=2026-08-12 11:17:07`（2 小时没结束）。
- `GET /api/jobs/status` → `last_discover = null`（从未成功完成过一次）。
- `POST /api/jobs/discover/run` → **409 冲突**（因 `task_queue.has_active("daily_pipeline")` 判定已有任务在跑）。
- `data/logs/app.log`：11:17 之后只有「数据源 kline/index_spot 已降级到备用接口」海量刷屏，**全程无「候选池落库完成」「discover 完成」**。

### 为什么卡死 + 为什么这么慢（慢的根因）
1. **卡死点**：discover 的「威科夫相对结构列」阶段（`app/agents/discover.py:_fill_wyckoff_columns`）要对**硬过滤后的 300 只**股票，每只调一次 `fetch_daily_kline(code, 近400天, 今天)` 拉 400 天日K。
2. **触发降级**：11:17 那一刻东财 `stock_zh_a_hist` 主源降级（日志全是「kline 已降级到备用接口」），单请求 15s 超时 + 重试（`settings.datasource_retry_times/timeout`），300 只并行线程池全被 15s 超时拖住 → 整体指数级变慢，卡到 2 小时。
3. **对比**：8/10 晚 23:14 那次东财主源通（`威科夫计算完成` 后 1 分钟内落库），1 分钟跑完；今天主源降级就卡死。**东财接口当时限流/超时是直接触发点**（此刻实测东财 0.8s/股已恢复，但卡死的任务不会自己恢复）。

## 三、优化方案（请你评估后执行）

### 方案 A · 应急恢复（让 8/12 候选池尽快出来）
**请先做这个，恢复服务可用。**
1. 用 Claude Code 重启后端服务（你是通过 bash 拉起的 `backend/scripts/dev_run.py`，请按你的同一套方式重启；**彻底停掉当前所有后端实例**，确认 8000 端口被干净释放再启，避免多实例残留）。
2. 重启后先 `POST /api/jobs/discover/run` 手动触发一次 discover。**确认**：
   - 返回 `task_id` 而不是 409。
   - 轮询 `GET /api/tasks/{tid}` 或 `GET /api/tasks/recent` 看到它 `status=done`、`error` 为空。
   - `GET /api/jobs/status` 里 `last_discover` 变成今天。
   - 数据库确认：`SELECT MAX(trade_date), MAX(created_at) FROM stock_candidate;` 出现 2026-08-12。
3. 若仍卡死，回看 `data/logs/app.log` 是否又有「kline 已降级」刷屏；若东财仍降级，可临时跳过威科夫或延长等待，但**先排查为何降级**。

### 方案 B · 根治（解决"任务卡死永远占锁"）—— 强烈建议
本次最该改的代码，防止再发生：

1. **后台任务加"卡死超时终结"**（`backend/app/services/task_queue.py`，`submit`/执行线程）：
   - 给 `daily_pipeline`、`monitor_all` 这类长任务设**超时上限**（建议 30~40 分钟）。
   - 超时未完成 → 强制标记任务 `status=failed, error="timeout"` 并**释放 its task lock / active 标记**，让新的 discover 能进来。
   - 提供**手动强制取消**接口：`POST /api/tasks/{tid}/cancel`，允许杀掉 running 状态的卡死任务（当前只有 failed 才能 retry，running 无法干预）。

2. **discover 数据获取阶段加整体超时 + 容错**（`backend/app/agents/discover.py:_fill_wyckoff_columns`）：
   - 给 300 只威科夫整体加**超时预算**（如 10 分钟），超时未算完的股打 WARNING 跳过/用空结构列继续，**绝不无限等**。
   - 单请求超时 `15s → 5s`（`akshare_source.py`），降级时快速失败而非长时间阻塞线程池。

3. **多实例防护**（可选，堵住"多个后端同时跑调度/抢任务"）：
   - 后端启动时用**单例锁或端口探测**（8000 已被占用则拒绝再启），避免 run_dev.bat 和 Claude Code 各拉一份、两个 APScheduler 抢同一个 `daily_discover` 锁。

### 方案 C · 数据源降级健壮性（中远期）
- `index_spot` / `kline` 主源（东财）降级时，当前是「等待 15s 超时→切新浪」；建议改成**主源快速失败探测**（如 3s 内无响应立即切备用），减少单股阻塞时间。
- 东财接口限流是常态，可给 kline 加**进程级并发上限**（如同时最多 20 个请求），防止 300 只并发把东财打限流。
