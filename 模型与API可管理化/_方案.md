# 模型与 API 可管理化方案

## 1. 文档定位

原文件在工作区中不存在，无法从中断点逐字恢复。本稿依据当前代码锚点重建，保留可执行的设计结论和治理红线。

## 2. 核心判断

当前系统已经具备模型调用的可用基础：配置集中在 Settings，结构化调用区分 LIGHT 与 DEEP，调用结果有 Pydantic 校验和有限重试，缓存键包含模型身份，统计服务记录请求、Token、成本和模型分布。因此主要问题是“可管理性与可审计性不足”，不是再增加一套平行的 LLM 抽象。

管理化应把模型/API 作为受控配置对象来管理，同时保留现有调用边界。凭据必须继续由环境变量或密钥存储提供；管理界面只显示掩码；路由和预算变更必须有版本、审计和回滚；模型能力不匹配时要明确失败或进入有限、可解释的降级链。

任何阶段都不得引入自动下单、自动交易、绕过 Audit Gate 的规则采纳、把 shadow 知识写入正式提示词或评分、让 ReAct 工具修改业务状态，也不得把明文 API Key 写入数据库、日志、缓存、提示词或前端响应。

## 4. 目标与非目标

### 4.1 目标

1. 能查看 Provider、模型别名、能力、当前状态、路由优先级和配置版本。
2. 能在不暴露凭据的情况下验证连接、验证模型能力和预览路由结果。
3. 能管理非敏感路由、预算、超时和开关，并保留审计记录、版本和回滚点。
4. 让调用日志、缓存身份、统计成本和配置版本相互对应。
5. 在故障、超额或能力不匹配时给出可解释的有限降级。
6. 为新增 Provider、Agent 和模型能力提供一致的复用模式。

### 4.2 非目标

- 不重写现有 structured LLM 调用协议。
- 不允许普通 Agent、用户对话或 ReAct 工具直接修改规则、知识、记忆、路由或凭据。
- 不把模型管理做成自动交易控制台。
- 不在本阶段承诺跨 Provider 的完全参数兼容。
- 不将 shadow 结果直接纳入正式评分、提示词或生产路由。

## 5. 管理对象模型

### 5.1 Provider

字段建议：provider_id、显示名、协议类型、基础 URL（可显示主机和路径，敏感查询参数掩码）、启用状态、健康状态、配置版本、最近检查时间、负责人和备注。

Provider 只描述接入方，不承载某个 Agent 的业务规则。协议适配应复用现有 OpenAI 兼容客户端，特殊协议必须单独声明能力和测试矩阵。

### 5.2 Model Profile

字段建议：profile_id、Provider、模型名、内部别名、能力集合、上下文上限、默认最大输出 Token、价格版本、状态、优先级、生效时间和失效时间。

能力至少区分：chat、structured_json、reasoning、vision、embedding、batch。能力声明必须由连接测试或供应商资料验证，不能只由名称推断。

### 5.3 Credential Reference

保存密钥引用而非密钥正文，例如环境变量名、外部 Secret ID 或部署平台的引用。响应只返回“已配置/未配置”和掩码后的末四位（如有必要）；读取接口永远不返回可复原的完整值。

### 5.4 Routing Policy

字段建议：业务能力、Agent/任务范围、首选 profile、候选 fallback、触发条件、超时、Token 上限、预算上限、版本、审批状态和生效窗口。

路由策略只能选择已登记且能力匹配的 profile。策略版本要进入调用上下文和审计事件，确保缓存和统计可追溯。

### 5.5 Health and Budget Policy

健康策略包括超时阈值、连续错误阈值、熔断时间和探测间隔。预算策略包括日/月 Token 额度、成本额度、单请求上限和告警阈值。策略只影响调用准入和降级，不得自动改变交易或业务规则。

## 6. 配置与存储分层

### 6.1 凭据层

凭据继续由环境变量或 Secret Manager 注入。数据库只保存引用、轮换状态和校验元数据。导出、备份、错误堆栈、缓存键和前端状态均不得包含密钥正文。

### 6.2 管理层

Provider、Model Profile、能力声明、路由、预算、超时和开关可进入受控配置表或版本化配置文件。每次写入产生不可变版本记录，当前生效版本单独指向；回滚只切换到已审计版本。

### 6.3 运行层

进程启动时加载凭据和生效配置，形成只读运行快照。运行快照包含配置版本、模型身份和能力摘要，不包含秘密。热加载必须原子替换快照，失败时保留上一份有效快照。

### 6.4 用户和租户范围

全局 Provider/凭据属于系统管理员范围；Agent 默认路由属于系统配置；个人偏好仍使用现有用户偏好版本机制。用户偏好不能越过能力、预算、审计和安全策略。

## 7. 初始 Provider 与模型登记

| Provider | 现有配置锚点 | 初始用途 | 必验能力 |
|---|---|---|---|
| DeepSeek | deepseek_api_key、deepseek_base_url | 通用结构化调用，LIGHT/DEEP | chat、structured_json、reasoning（按 profile） |
| MiniMax | minimax_api_key、minimax_base_url | 视觉、体验 worker 等显式场景 | chat、vision（按启用项） |
| SiliconFlow | siliconflow_api_key、siliconflow_base_url | Embedding | embedding |
| Local | local_embedding_model | Embedding 本地回退 | embedding、离线可用性 |

DeepSeek 至少登记两个逻辑 profile：deepseek-light 对应默认轻量模型，deepseek-deep 对应推理模型。逻辑别名不能掩盖真实模型名；调用记录同时保留别名和实际名称。

MiniMax 的 OCR、视觉或 worker 能力按现有开关分别登记，未启用的能力不应出现在可选路由中。Embedding Provider 不得被误选为 chat 模型。

## 8. 路由设计

### 8.1 保留现有等级语义

ModelLevel.LIGHT 和 ModelLevel.DEEP 继续是上层调用的稳定接口。管理化只改变其背后的可配置映射、能力校验和可观测信息，不要求 Agent 逐个改写为 Provider 特定名称。

### 8.2 路由决策顺序

1. 根据任务声明取得所需能力和等级。
2. 读取生效的 Routing Policy 版本。
3. 过滤禁用、过期、能力不匹配、超预算或熔断中的 profile。
4. 按优先级选择首选 profile。
5. 失败时仅沿策略中明确列出的 fallback 链尝试。
6. 写入 route reason、候选列表摘要、实际 profile 和配置版本。

### 8.3 回退约束

现有 LIGHT→DEEP 回退保持最多一次升级和有限重试。跨 Provider 回退必须显式配置，且要满足同等能力、预算和数据边界。没有合格候选时返回明确错误分类，不返回伪造成功或无依据的零值。

### 8.4 参数归一化

只归一化跨 Provider 都有明确含义的参数，例如最大输出 Token、超时和 JSON 输出要求。reasoning、vision、工具调用等差异参数必须按能力声明处理；不支持时在路由前失败。

## 9. 凭据管理

- 管理页面采用写入即验证、读取只显示状态的模式。
- 更新凭据时仅提交到 Secret Manager 或环境注入层，业务数据库写入引用和版本。
- 连接测试使用最小请求，禁止把密钥写入请求日志、异常、追踪标签或缓存。
- 轮换采用新版本先验证、再切换、旧版本保留短暂回滚窗口的流程。
- 删除或失效凭据要先确认没有生效路由依赖，并记录审计事件。
- 任何导入、导出、诊断包都必须执行敏感字段扫描。

## 10. 管理 API 与 UI

### 10.1 只读接口

建议新增：

- GET /api/model-registry：返回 Provider、profile、能力、状态、配置版本和掩码信息。
- GET /api/model-registry/health：返回最近探测和错误分类。
- GET /api/model-routes：返回按 Agent/能力展开的生效策略。
- 继续使用 GET /api/llm/stats，增加配置版本、别名和路由原因维度时保持兼容。

### 10.2 校验和预览接口

- POST /api/model-registry/validate：校验字段、能力声明和凭据引用，不改变生效配置。
- POST /api/model-registry/test-connection：使用最小探测请求，返回成功、延迟、模型能力结果和可操作错误分类。
- POST /api/model-routes/preview：输入 Agent、任务能力、等级和预算上下文，返回候选及淘汰原因，不实际调用模型。

### 10.3 受控写接口

- POST /api/model-routes/draft：创建草稿版本。
- POST /api/model-routes/submit：提交审核。
- POST /api/model-routes/activate：仅审核通过且具备管理员权限时切换生效版本。
- POST /api/model-routes/rollback：切换到已审计的上一版本。
- GET /api/model-config/audit：查询变更人、原因、diff 摘要、审批状态和时间。

凭据更新与路由激活分离，避免一次请求同时改变秘密和生产行为。多用户模式必须执行管理员校验；单用户模式也要保留审计事件。

### 10.4 UI 交互

首屏显示当前生效版本、Provider 健康、模型能力和预算使用。编辑流程采用草稿、校验、连接测试、预览、提交审核、激活的顺序。密钥输入框不可回显，错误提示只显示分类和追踪 ID。

## 11. 可观测性与审计

每次模型请求至少记录：request_id、user/tenant（按权限脱敏）、Agent、任务类型、逻辑 profile、实际 Provider/模型、ModelLevel、路由策略版本、配置版本、回退原因、开始/结束时间、延迟、Token、缓存命中、错误分类和重试次数。

提示词和响应正文按现有业务隐私策略处理；审计日志只保留必要摘要，绝不记录 API Key。对于包含用户敏感内容的上下文，记录哈希或长度等不可逆指标。

配置审计事件至少包含：对象类型、对象 ID、旧版本、新版本、变更人、变更原因、审批人、校验结果、激活时间和回滚关系。审计记录不可由普通 Agent 删除或改写。

## 12. 缓存、版本与一致性

缓存身份必须包含实际模型身份、逻辑 profile、路由策略版本，以及会影响输出的配置版本。现有 user preference version 和 context hash 继续保留。模型别名指向变化时，即使真实模型名相同，也应通过 profile/config version 区分缓存。

以下变更需要使相关缓存失效或自然失配：模型映射、系统提示词、结构化 schema、Embedding 模型、温度/采样策略、工具集合和输出 Token 上限。仅修改展示名、备注或健康探测时间不应清空业务缓存。

热加载采用“校验完整快照→原子替换→发布配置版本事件”的顺序。任何校验失败都不得替换当前有效快照。

## 13. 故障与降级

| 场景 | 行为 | 禁止行为 |
|---|---|---|
| Provider 超时 | 按策略有限重试或进入明确 fallback | 无限重试、静默跨域 |
| 模型能力不符 | 路由前拒绝并返回能力错误 | 发送不兼容请求后伪造成功 |
| 预算超限 | 拒绝、降级到已批准候选或等待下一周期 | 自动修改预算或业务规则 |
| 凭据缺失 | 标记不可用，保留上一有效快照 | 输出密钥、使用未知凭据 |
| Embedding 远端故障 | 仅按策略切本地 embedding | 把 chat 模型当 embedding |
| 配置热加载失败 | 保留上一版本并告警 | 部分字段生效 |
| 结构化校验失败 | 使用现有有限重试/等级回退 | 返回未校验对象 |

所有降级都要能在统计和审计中回答“为什么降级、降到哪里、是否成功”。

## 14. 治理红线

1. 模型管理不能改变系统地图、Agent 边界或核心规则的所有权。
2. RuleChange 必须进入 Audit Gate；模型配置激活不能代替规则审核。
3. shadow 知识、影子评分和实验路由只能用于对照和验证，不能直接进入正式提示词、评分或生产策略。
4. 记忆保持软上下文属性，必须有范围、状态、置信度和过期控制。
5. ReAct 工具保持只读：不能改模型配置、发告警、批准审计、修改业务状态或下单。
6. 不允许任何自动交易、自动下单、自动调仓或以模型管理接口触发交易动作。
7. 普通 Agent 和用户对话不能写入凭据、规则、知识、记忆或生产路由。
8. 运行日志、缓存、错误响应和导出文件不得出现明文秘密。

## 15. 分批实施

### 批次一：只读登记与状态

建立 Provider/Profile 数据结构和只读接口，接入现有配置的掩码展示、能力摘要、健康状态、配置版本和 /api/llm/stats 兼容视图。此批次不改变实际路由。

验收：能列出 DeepSeek、MiniMax、SiliconFlow、Local；秘密只显示状态；未知能力不可被选择；接口在缺少可选 Provider 时仍返回明确状态。

### 批次二：连接测试与路由预览

增加最小探测、能力验证和不执行实际调用的路由预览。把 LIGHT→DEEP 以及显式跨 Provider fallback 的原因写入测试结果和观测事件。

验收：探测失败有分类；预览能解释每个候选为何保留或淘汰；测试不会写入生产配置、缓存或业务状态。

### 批次三：非敏感配置草稿、审核和激活

增加版本化草稿、diff、审批、激活、回滚和原子热加载。先支持路由、预算、超时、开关等非敏感字段；凭据只接 Secret Reference。

验收：普通用户无法激活；审批前不影响运行；激活后调用和缓存能看到新版本；回滚可恢复上一有效版本。

### 批次四：管理 UI 与运营闭环

实现列表、详情、健康、预算、路由预览、审计和回滚页面。错误只呈现可操作分类和 request_id，不展示内部秘密或完整提示词。

验收：桌面和窄屏下字段不重叠；高风险操作有明确二次确认和审计；只读用户无法看到写控件或敏感值。

### 批次五：影子验证与逐步放量

新增 Provider 或改变生产路由前，先在 shadow 范围执行对照，比较成功率、结构化通过率、延迟、Token 和成本。shadow 结果只用于评审，不能直接升级为生产配置。

验收：达到预设阈值并完成审核后才允许激活；任何回归都有可回滚版本和责任人。

## 16. 验收矩阵与最小测试

| 类别 | 最小检查 |
|---|---|
| 配置 | 环境变量加载、缺失值、掩码、引用不可回显 |
| 能力 | chat/JSON/reasoning/vision/embedding 过滤准确 |
| 路由 | LIGHT/DEEP 映射、显式 fallback、预算和熔断 |
| 调用 | 重试上限、结构化校验、错误分类、request_id |
| 缓存 | profile/实际模型/配置版本变化后的键隔离 |
| 统计 | 命中、Token、成本、模型分布与版本对应 |
| 审计 | 草稿、审批、激活、回滚记录完整且不可越权 |
| 安全 | 日志、异常、响应、导出无明文密钥 |
| 治理 | 无规则绕过、无 shadow 晋升、无 ReAct 写入、无交易动作 |

仅文档重建阶段不运行代码测试。进入实现批次后，按 AGENTS.md 要求先跑与改动直接相关的测试文件；发现跨模块契约变化再扩大范围。

## 17. 复用模式

新增 Provider 时复用“Provider→Profile→Capability→Routing Policy→Health/Budget→Audit”链路，不在 Agent 内硬编码 URL、模型名或密钥。新增 Agent 时声明所需能力和 ModelLevel，调用统一路由服务；不得自行读取秘密或绕过统计。

新增能力时先扩展能力枚举、验证器、预览和测试矩阵，再开放到路由策略。新增降级链时必须同时补充触发原因、预算约束、审计字段和回滚方案。

## 18. 待确认事项与遗留项

1. 生产环境是否已有 Secret Manager；若没有，先确定部署平台的密钥注入方式。
2. 配置持久化采用现有数据库、独立配置表还是版本化文件，需要结合部署拓扑决定。
3. MiniMax 各能力的真实模型清单、视觉输入格式和价格版本需要由运行环境验证。
4. 是否允许按租户配置独立预算和 Provider；若允许，需补充隔离与审计字段。
5. 健康探测频率、熔断阈值和预算阈值应以历史统计校准，不能先写死为业务规则。
6. UI 实施前需确认现有前端路由、权限组件和错误展示规范。

在上述事项明确前，不应直接把新的模型配置写接口接入生产激活流程；可以先完成只读登记、连接测试和路由预览。
